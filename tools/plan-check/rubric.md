# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diagnosis-Grounded | The plan's stated cause (its diagnosis/"cause"/"problem statement" section), read against every step and output in the repro-evidence block, plus any thread comment the diagnosis cites. | Pass if every claim the diagnosis makes about the mechanism is either directly shown by a step/output in the repro evidence, or the plan itself flags it as an unverified assumption (not asserted as fact). Fail if the diagnosis is contradicted by a step in the repro evidence (e.g. a control run rules the claimed mechanism out, or a step shows the symptom occurring where the claimed mechanism could not apply), or if the diagnosis relies solely on an unverified thread comment ("X claims...", "X says the root cause is...") presented as settled fact while the repro evidence never independently confirms it. Unclear (repro evidence neither confirms nor contradicts, and the plan does not flag the gap) counts as fail. | required |
| Scope-Bounded | The plan's scope statement (in-scope / not-in-scope, or equivalent) and its list of changes/files/areas. | Pass if the described change is one fix confined to what the diagnosed cause requires, with anything adjacent explicitly named out of scope. Fail if the plan adds work beyond fixing the diagnosed cause: unrelated refactors, version/dependency upgrades, new abstractions, multi-file "while I'm in there" changes, or a rewrite that buries the actual fix inside a broader redesign. A plan with no scope statement at all, whose changes list is already narrow and matches the diagnosis, still passes; a plan whose changes list visibly exceeds the diagnosis fails regardless of whether it labels itself "in scope." | required |
| Executable | The plan's approach/changes section: the files, functions, or code locations named and the steps to take. | Pass if a stranger with no access to the plan's author could start implementing immediately: at least one concrete file, module, or code path is named, the mechanism of the fix is stated (what will be added, changed, or drained/consumed, and roughly where in the flow), and any deferred detail is a normal implementation step (pinning the exact function name once inside the file) rather than the location or mechanism itself being unknown. Fail if the plan's steps are "investigate," "profile," "look into," "figure out where X lives," "dig into the code," or "poke around" with no location or mechanism named at all — i.e. the plan is a promise to go find a plan, not a plan. Naming a module or path plus a stated mechanism passes even without a specific function name. | required |
| Test-Plan-Decisive | The plan's test plan, read against the repro-evidence block's steps and artifacts. | Pass if the test plan names a specific, observable outcome tied to the actual reported behavior — typically re-running the repro evidence's own steps and stating what result confirms the fix (an exact color/exit code/timing/output changing in a stated way). Fail if the test plan is generic and content-free regardless of what the fix is ("make sure nothing regresses," "should work," "should feel fast," "confirm it's fixed") or checks something other than the diagnosed behavior. | required |
| Honesty | The plan's stated risks, unknowns, or open questions, read against how confidently the rest of the plan is written. | Pass if genuine unknowns (unmeasured costs, untested edge cases, alternative approaches not yet ruled out) are named as unknowns rather than asserted as settled, OR the plan has no material unknowns left to flag. Fail if the plan asserts a claim as fact that the plan's own evidence does not establish (dressing up a guess as certainty) without ever calling it a guess. | preferred |
| Comms-Thread-Aware | The plan comment, read against the thread-highlights block for explicit maintainer-stated direction, and against the repo-facts block's stated contribution/AI-use policy. | Pass if the comment does not contradict or silently ignore an explicit direction a maintainer/collaborator already gave in the thread (a named cause, a named fix location, a request for specific testing, a rejected approach) — the plan may disagree with that direction, but only by engaging it, not by proceeding as if it were never said — AND the comment satisfies the repo's stated AI-use policy: if the policy requires an explicit disclosure statement (tool used, extent of assistance), the comment (or plan) contains one; if the policy only requires human-voiced text with no disclosure sentence, the comment reads as a specific, human-voiced account rather than generic/templated text; if the repo states no AI policy, this half of the check passes by default. Fail if either half fails. | required |

## Verdict rule

Accept only if every `required` check passes. Any `required` check graded
`fail` holds the package at `reject`. `preferred` checks (Honesty) are
reported but never change the verdict. `unclear` is treated as `fail`
for every check, required or preferred, per the Diagnosis-Grounded and
Test-Plan-Decisive conditions above and as the default whenever a
check's own pass condition does not resolve cleanly from the package —
a plan the package leaves genuinely ambiguous is not ready to build
from.
