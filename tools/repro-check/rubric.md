# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Environment-Recorded | The repro report's environment line, read against the issue's stated target (OS, tool version, relevant runtime/library versions) | Pass if the report names the OS and every version the issue's bug depends on (tool version at minimum; language/runtime/library version if the issue turns on one). If the tested version differs from the issue's reported version, pass only if that delta is stated explicitly, not left for the reader to notice. Fail if no environment line exists at all, or if a version-dependent bug is tested on a different version with no acknowledgement of the gap. | required |
| Steps-Followable | The repro report's numbered steps or commands, read against whether a stranger with no access to the reporter's machine could run them | Pass if every step is a command, config, or input a stranger could type or create themselves from what's shown (inline config content, inline input files, exact CLI invocations). Fail if a step depends on a private/unshared resource (an internal monorepo, an unshared config file, credentials, a machine only the author has), or skips the specific trigger condition the issue names (e.g., testing a different flag/syntax than the one reported). | required |
| Behavior-Matches-Issue | The artifact (output excerpt, log, screenshot) in the repro report, read against the exact behavior the issue describes (error type, exit code, message, or symptom) | Pass if the shown artifact demonstrates the same behavior class the issue reports (same error/crash/message, not just "something went wrong"), on the trigger the issue actually names. Fail if the artifact shows an adjacent symptom (e.g., a graceful validation error standing in for a reported panic/crash, or a compile error instead of a runtime path expression error) even if the report narrates it as a match. | required |
| Evidence-Not-Assertion | The report's primary claimed behavior (the one the issue is about), read against whether a concrete artifact (command output, log line, screenshot) backs it | Pass if the primary behavior has a shown transcript or output backing it. A secondary confirmatory detail (e.g., a control run's result stated in prose, like "dropping flag X gives the correct output") does not need its own separate output block as long as the primary artifact is shown and the stated detail is a plain factual description, not a new unverifiable claim. Fail if the report asserts a conclusion about the primary behavior (root cause, "guaranteed reproducible," "I verified this") without showing the transcript or output that produced it, or if the shown artifact demonstrates something other than what the "expected/actual" text claims it does. | required |
| Honest-Outcome | The report's stated outcome (reproduced / did not reproduce), read against what the artifacts actually show, including any acknowledged environment differences | Pass if the report's conclusion matches its evidence: a reproduced bug is shown reproduced, and an honest cannot-reproduce names what was tried, what differed from the issue's setup, and a concrete hypothesis for the gap. Fail if the report claims a stronger outcome (confirmed root cause, definite reproduction) than the shown evidence supports. | required |
| Claim-Specificity | The candidate claim comment, read on its own | Pass if the claim names the specific issue/behavior it is about and states a concrete next investigative step (not a promised fix or date). Fail if the claim is generic boilerplate interchangeable across issues ("assign me," "+1, can confirm," a promised fix/timeline) with no specifics tying it to this issue. | required |
| AI-Disclosure | The repo-facts block's stated contribution/AI-use policy, read against the claim comment and repro report text | Read the policy for which of two distinct rules it states, if any. (a) A disclosure rule: comments must state that AI was used and to what extent. Pass only if the comments contain an explicit disclosure statement; fail if the policy states this rule and neither comment discloses (course packages are treated as AI-assisted work). (b) A human-voice rule: comments must be written by a human in their own words (no disclosure statement required, just no AI-generated-sounding text passed off as the contributor's own). Pass if the comments read as a specific, human-voiced account in the contributor's own words (not templated or AI-boilerplate-sounding); this rule does not require an explicit disclosure sentence. If the repo states neither rule (silent or a generic/permissive policy), pass by default. | required |

## Verdict rule

Accept if every required check passes. Reject if any required check fails or is unclear. `unclear` is treated as fail: there are no preferred checks in this rubric, so every check gates the verdict.
